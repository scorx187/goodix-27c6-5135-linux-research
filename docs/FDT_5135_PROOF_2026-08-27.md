# Goodix 27c6:5135 FDT down/up proof

Date: 2026-08-27

## Result

Linux successfully reproduced the ChicagoHS finger-detection state machine through manual baseline measurement, finger-down, and finger-up events.

```text
TLS session             PASS
FDT manual 0x36         PASS
FDT-down 0x32 ACK       PASS
FDT-down event          PASS
FDT-up 0x34 ACK         PASS
FDT-up event            PASS
```

## Manual mode

Windows evidence selects `ChicagoHUSetMode Mode 3 Type 3 base_type 1` for FDT manual acquisition.

On this device, the private Windows `goodix.dat` FDT block is 12 bytes representing six duplicated manual threshold bytes. Linux sends:

```text
0d 01 + private 12-byte FDT manual seed
```

The 16-byte event payload is parsed as:

```text
+0x00 IRQ status       u16 little-endian
+0x02 touch flag       u16 little-endian
+0x04 six zone values  6 * u16 little-endian
```

A finger-off baseline produced IRQ `0x0100`, touch flag `0x0000`, and six live zone values.

## FDT-down

For each live manual zone value:

```text
threshold = floor(raw_zone / 2)
encoded   = 80 threshold
```

Linux sends command `0x32` with:

```text
08 01
+ six 80/threshold pairs (12 bytes)
+ timestamp u16 little-endian
```

Total command payload length: 16 bytes.

Observed successful presses produced nonzero touch flags and 5/6 or 6/6 active zones.

## FDT-up

Windows trace proved command `0x34` and a 14-byte payload:

```text
0a 02 + six 80/threshold pairs
```

The proof run used a private, device-specific Windows-traced set of FDT-up thresholds. The repository should not pretend that a generic derivation has already been proven.

The Linux event returned:

```text
IRQ       0x0200
touchflag 0x0000
zones     0/6
```

## Timeout issue in upstream code

The upstream `goodix.py` FDT helpers use `protocol.read(timeout=None)` for the event read. On USB this becomes an infinite libusb timeout. During reverse engineering this made an incorrect FDT-up threshold set appear to "hang" indefinitely.

Research probes should use a finite event timeout and separate ACK success from event success.

## Failed attempts worth preserving

### v2

FDT-down transport/event worked, but the script misinterpreted the 12-byte `goodix.dat` FDT block as six raw `u16` values and saturated down thresholds. It then used an unproven FDT-up derivation and hung waiting for an event.

Useful conclusion: command/event transport was valid; calibration interpretation was not.

### v3

Stopped before sensor I/O because it incorrectly assumed the private FDT block was already six `0x80 xx` threshold pairs.

Useful conclusion: the FDT block is duplicated manual seed bytes.

### v4

Stopped at chip guard because register `0x0000` read `06000000`. This led to the activation-sequence investigation.

### v5

Added the verified activation sequence and completed manual/down/up successfully.
